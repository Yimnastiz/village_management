# Documentation Source of Truth

The final formal actors are exactly สมาชิก (Resident) and ผู้ใหญ่บ้าน (Headman). There is no Public / Guest actor in the formal system analysis or documentation. Headman is the sole administrator and uses `/admin` for all active administrative work.

Each runtime installation resolves exactly one active Village. Public routing, registration, feedback, and authenticated access are all bound to that configured Village; zero or multiple active Village rows are a configuration error. Legacy Village and membership rows remain historical data and grant no workspace access. Public route accessibility is separate from formal actor modeling.

Unauthenticated member-facing lifecycle flows remain valid. A request to open a บัญชีประจำบ้าน may be submitted before the requester has an activated Resident account. Feedback, complaints, and website-error reports may also remain available before login when that is the intended runtime behavior. For formal Use Case analysis, these flows belong to สมาชิก (Resident); they do not create a third Public / Guest actor and do not require authentication merely to match the actor model.

Headman owns Feedback (`/admin/feedback`), Village Broadcasts (`/admin/broadcasts`), Audit (`/admin/security`), System Settings (`/admin/settings/system`), Village Settings (`/admin/settings/village`), and the existing village operational modules.

During Maintenance Mode, normal Admin work is blocked while the authenticated Headman may reach `/admin/settings/system` to disable maintenance. No Super Admin recovery path exists.

The final two-actor model does not change the account architecture: one Village installation; one House with at most one Resident House Account; one Resident House Account backed by one Resident User; multiple verified อีเมลสำหรับเข้าสู่ระบบ for that same House Account; and Person/population records that are not authentication identities. Resident and Headman login use email plus an email verification code, and the server determines account type. There is no Super Admin runtime, no `SystemRole` enum or field, no Assistant Headman, and no Assistant membership enum value. Active authority and current administrative classification derive solely from an ACTIVE HEADMAN membership; Resident has no administrative authority. Historical audit, notification, broadcast, issue-message, and appointment metadata can still render legacy Assistant and Super Admin labels through string-based compatibility helpers. `HouseSourceType.SUPERADMIN_CREATED` is intentionally retained only as historical House provenance and is not an active actor or role.
